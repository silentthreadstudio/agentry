description: Land one task (or debt item) on main — preflight, the repo's own checks, cherry-pick, the gate (or the recorded gate it may trust), the board's done row, SHA and handoff line in one commit, then push per policy and cleanup. Stops at the first red step.

Land task `$ARGUMENTS` on main. A debt id (`DEBT-2`) lands the same way. A debt kind declared in `exec.kinds` gets the done status and the commit and no handoff line (the record row says `no handoff: debt is outside the tree`), so `--summary` is not needed. A debt kept as an ordinary task in the lifecycle board writes a handoff line like any task, and needs a summary (declaring a debt kind is in the workflows docs, `exec.kinds`). What each row means and every edge case: the `conducting` skill's `references/merge.md`.

Shell calls use the plugin's `agentry` bin `command` when it is on PATH; otherwise run `node "plugin/bin/agentry" <board|lane|mem|draft|run|lock> …` with the same arguments.

Run each call from the main checkout, in the foreground, and read its exit code: 0 = done, `next` printed; 1 = a red step stopped it; 2 = usage or refusal. Never pipe it into `grep`/`tail` to decide. Show each step table as printed.

Before the first `--preflight`, main must be clean: `git status` empty, with the setup committed (`.agentry/process.json`, `.agentry/workflow.json`, the conductor prompt, `AGENTS.md`, the board rows `/agentry/new` added). Otherwise the `main` row is red and names each file; ask the owner to commit or undo them (never commit for them).

1. `agentry lane merge <id> --preflight`. Add `--branch <b>` only for work built outside `/agentry/exec` (it adopts that branch; `<b>` is the branch's name exactly as git lists it). To build on such work in a lane instead of landing it as it is, `agentry lane exec adopt <id> --branch <b>`.
2. For each repo check the table names, a skill in `extensions.merge.checks` or a manual `gate.checklist` item: run the skill's checks (or do what the item says), then `agentry lane merge <id> --check <name>=pass|fail --note "<one line>"`. A name that is neither is refused (exit 2) and both lists are shown. A check counts only for the branch tip it was recorded on.
3. `agentry lane merge <id> --message "<board commit message>" [--summary "<handoff text>"]`: the repo's commit conventions, no AI attribution. A land refuses over a dependency still open (the `deps` row, before any pick), naming the `board set` line that clears it. If the call dies (a host's time limit), run the same land again: it clears what it can prove it left and resumes; if it stops instead, follow `next`. The owner's uncommitted `guard.allow` files are set aside for the land and put back after it; a flagged item no verifier read does not land. Add `--drop-carry` only on the owner's call, when the table says exec's writes no longer apply. A `board set` or `board add --apply` the owner made on main is recorded and goes into the board commit; once the gate has passed, the owner's commit of a board fix (board files and `.agentry/*.json` only) is accepted and the board commit goes on top.
4. Follow `next`. `ask` → ask the owner, and add `--approved` only on their yes. `never` → no push. Then `--cleanup` (it discards `cleanup.disposable` files on its own). If it refuses on other ignored files, show them and ask; `--discard-ignored` only on a yes.

A stacked lane (`stack` row red) lands only after its parent: land the parent first, then follow the row's `next` (`agentry lane exec restack <id>`, its gate, the land). A parent's land restacks each child at rest onto main and names the ones it left (an agent out, or a conflict with its `--main` restack line).

A land left in `merging` that cannot go on (`exec start` says main is mid-land) is closed only on the owner's call: `agentry lane merge <id> --resolve landed` when every pick is on main (the ledger is merged; the board record is the owner's), or `--resolve rolled-back` when none is (the lane is verified again). Each checks main first, refuses with what it found (the ledger still holding set-aside edits, git mid-pick, a pick on main for `rolled-back`) and touches neither main nor the board; a `landed` lane leaves the board's done row and handoff line to the owner and names any lane stacked on it for `lane exec restack <id> --main`.

A verified lane whose work reached main another way (a fast-forward of a combined branch, a squash), so the preflight finds nothing to land, is closed the same way: `agentry lane merge <id> --resolve landed`. It reads `git cherry` over the lane's own commits (`base..tip`): with every one on main by patch the ledger is merged (`merge.how: "found-on-main"`), nothing picked and no commit made; it refuses when any has no matching patch on main, naming each (short SHA and subject). Add `--checked` only once the owner has checked by hand that those landed squashed or reworded; it is recorded in the ledger. A lane stopped on a red gate after a passing verdict closes the same way. It runs only with the main checkout on the main branch and the lane's branch at or past the tip it was verified on (a verified lane: at its `closedTip`); commits after that tip are named as unverified and close only with `--checked`, or go through `lane exec restart <id> --carry` to be verified again. It names any uncommitted work left in the lane's worktree, which `--cleanup` then refuses over. The board record stays the owner's, a parent closed so counts as landed for its stacked lanes, and `--cleanup` follows as after a land. "Found on main" is by patch, not by tree: a commit that landed and was then reverted on main still counts as found. git's patch id ignores whitespace, so check a lane's whitespace-significant files (Python, YAML, Makefiles) by hand before closing it.

On exit 1 or 2, stop and show why. Do what `next` says, or ask the owner. Never finish a step by hand: no hand cherry-pick, reset, board edit, commit or push.
