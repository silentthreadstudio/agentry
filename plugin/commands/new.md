---
description: Add one item of any kind this repo's process knows — task, sprint, question, decision, or whatever init learned — to every place that kind lives. Asks only that kind's fields; never commits.
argument-hint: "<kind> [title or text]"
---

Add one item. `$ARGUMENTS`: the first word is the kind, the rest is its title or text. Load the `process` skill;

1. **Kind.** No `.agentry/process.json` → say so, point to `/agentry:init`, stop. Read the kinds with `agentry board explain --json`; a missing or unknown kind → list the learned kinds and ask. A kind with no `create` → say no create rule was learned for it and offer `/agentry:init --relearn <kind>`.
2. **Decision drafts.** For `decision`, run `agentry board draft list` first and follow the skill's `references/drafts.md`: show each pending decision draft and let the owner apply it (`agentry board draft apply <n>` shows what it would add; on OK, `agentry board draft apply <n> --apply` adds the decision and ends this command for that item), drop it (to edit one, drop it and add the corrected draft), or go on to a new decision.
3. **Before.** Run `agentry board check --json` and keep its findings for the delta.
4. **Ask only the kind's `create.ask` fields**, minus what `$ARGUMENTS` already gave, in one `AskUserQuestion`: a ref or list field offers the existing ids of its kind (id, name, status) as options; a field with a fixed set of values offers those. The id: `agentry board next-id <kind>` when `create.id` is a pattern (show it, let the user change it), asked when it is `ask`. A block with `under: "ask"` → ask which heading, from the file's headings, and pass it as its text (`Sprint A1`). Leading `#` marks, when given, must match the heading's level: `## Sprint A1` finds only a level-2 heading.
5. **Show exactly what will be written**: run `agentry board add <kind> --fields '<json>'` (no `--apply`). It writes nothing and prints every `create` location with the lines it would get, the id it would take and any location it would skip; show that as printed. The JSON holds every asked field, a top-level `under` for an asked heading, and `id` when the user chose one or `create.id` is `ask`; with a pattern and no `id`, `add` fills the next one itself. One single-quoted argument, `'` written as `'\''`. Exit 2 → nothing would be written: show the reason and stop. Point out anything that looks like drift (a heading that names the parent differently from the board), but don't fix it.
6. **Write**, once the user confirms that preview: the same call with `--apply` and the `id` the preview printed (`agentry board add <kind> --fields '<json>' --apply`), so the write takes the same id; it reports it (`added task T7`). Exit 2 → nothing was written: show the reason and stop. Relay every location it reports as skipped.
   **A task's contract.** `/agentry:exec` builds only a task whose contract block `agentry board contract <id>` finds. When `add` reports `no contract for <id>`, offer to write the block it names (owns, exposes, acceptance) into that file in the same turn; if the owner declines, say plainly that the task is not ready for `/agentry:exec` until it has one. The `ready-has-contract` rule reports the same gap on any open task.
7. **After.** Run `agentry board check --json` and report the delta: "no new problems", or each new finding. Close with where the item now stands (status, parent, what it waits on).

Never edit the board files by hand, never commit.
