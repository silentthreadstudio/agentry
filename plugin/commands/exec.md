---
description: Build one task (or debt item) whose contract is already written. `agentry lane exec` cuts its worktree, writes the board, briefs a builder and an independent verifier round by round, and closes on a recorded gate with an episode. No spec, plan or split; no merge or push.
argument-hint: <task or debt id, as written on the repo's board>
---

Run the **exec lane** for task `$ARGUMENTS`: an item of the lifecycle's kind, or of a kind in `exec.kinds` (a debt id such as `DEBT-2`, built from its light contract, outside the sprints). The script carries the sequence: run the step it names and dispatch the prompt it prints, nothing else. The rules are in the `conducting` skill's `references/lanes.md`.

Shell calls use `agentry`, the plugin's `bin/` command; where it is not on PATH, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/board.mjs"` (or `lane.mjs`) with the same arguments.

1. Only for an id matching `^[A-Za-z0-9][A-Za-z0-9._-]*$` (otherwise ask first), run `agentry lane exec start '<id>'` in the main checkout. Exit 2: show the message (contract candidates, open writers, a light contract missing its Owns or Acceptance line, an id two kinds hold) and stop. Never guess a contract.
2. Read the printed text (`--json` prints the same fields as one object) and act on `next`. After `start`, check the `owned` list against the contract; a wrong list is fixed with the `amend` line (`agentry lane exec owns <id> --set <paths> --apply`), which also rewrites the waiting brief (`owns <id> --add <paths> --apply` appends files a builder asked for and does not own, for a lane in `needs-context` or held for context):
   - `build`, `verify`, `final`, `resolve`: dispatch a fresh agent with `prompt`, verbatim, as the whole prompt. `dispatch.agent` names the type (for a build it is a suggestion: you decide designer or implementer). When a `model` is printed, dispatch with that model. No worktree isolation option: the worktree exists.
   - `fix`, `recheck`, `needs-context`, `resend`, `continue`, `rebase`: when `mode` is `resume`, send `prompt` to the agent `agent` (resume it); otherwise dispatch fresh as above. For `needs-context`, do `todo` first.
   - `resume` (state `held`): the lane waits for the owner. A builder that reports `NEEDS_CONTEXT` a second time in the same step holds the lane for more context (`held: the builder needs more context again`, the question under `asks:`): answer with the fact, with the `owns --add` line when the report names files outside `owns`, or restart the lane with its work (3f); `hold` is refused on it. A flagged item whose verdict leaves notes open at the notes cap holds for the owner too: `resume` closes it as it is, `agentry lane exec fix '<id>' --owner "<the change>"` sends it back. Show them the `held:` line and its evidence, then stop and wait. When they answer, run the `run:` line with their words as `--note` (`--redo` when they send the run back: "change it first"; the fact itself for a builder that needs more context, or the `owns --add` line it names, then resume). Never resume on their behalf. A resume refused for main edits or `lanes.maxWriters` says what to clear first.
   - `gate`, `close`: run `run` and read its exit code (after a `report` with `route` not `all`, a `gate` next is an item with no verifier: the gate is its only check) (a gate past the host's foreground limit: `lanes.md`, Dispatching).
   - `stop`: tell the owner `reason`, with every verdict (`agentry lane exec show <id>`). Don't retry by hand.
   - `merge`: the lane is done; hand off (step 4).
3. When an agent returns, save its full reply to `reportPath` if that file is missing or empty, then run `after` with the agent's id. Back to step 2.
3b. A verdict of `PASS WITH NOTES` whose notes are worth fixing in this lane: before `close`, run the `notes:` line it prints (`agentry lane exec fix '<id>' --notes N1,N3`, the labels in the verifier's report) and carry on from step 2. `notes kept open (exec.noteRounds is <n>)` means the budget (read live from the workflow file) is spent: the notes go to the owner with the handoff, except on a flagged item, which holds for the owner instead. A verified lane the owner wants changed goes back with `agentry lane exec fix '<id>' --owner "<the change>"` (one builder round, then the lane's usual recheck).
3d. A land that stops on a cherry-pick conflict (or a branch moved since the lane closed) names `agentry lane exec rebase '<id>'`: run it and carry on from step 2 (`rebase` resumes the builder, `resolve` is a fresh verifier on the range-diff). A lane closed with no verifier whose item is flagged since: `agentry lane exec reverify '<id>'`.
3e. Stacked work (A45): `agentry lane exec start '<id>' --on '<parent>'` cuts the lane from a parent lane that is verified, held or at its gate. Each step then prints `stack:`; once it names a restack (the parent moved, landed or stopped), run `agentry lane exec restack '<id>'` when the lane is at its gate, close or merge (its gate refuses until then; `--main` takes it off a stopped parent, on the owner's call). It is refused on a lane held by a guard trip (run its report once main is fixed, then restack) and on a parked verified lane (resume it, then restack). Exit 1 is a conflict, aborted with nothing changed: show the owner the line, which names how to resolve it by hand; a hand resolution gets a resolution check (`resolve`). The lane lands after its parent (`/agentry:merge`).
3c. The owner wants to look while a builder works: once its reply is saved, `agentry lane exec hold '<id>' --for owner` holds the lane (`--evidence <path>` for what to open). A builder that is gone (`show` prints `idle:`): `agentry lane exec hold '<id>' --for later --note "<why>"` parks the lane with its worktree as it is; `agentry lane exec resume '<id>' --note "<why>" --fresh` later sends a fresh builder.
3f. A lane to throw away and start again (a resume refused because main touched its files names it, and so does a stopped lane's `ways on:`): `agentry lane exec restart '<id>' --carry` on a lane that is not merged and has no agent out archives it as `<id>.<n>`, cuts it again from main with its commits and uncommitted diff, and its brief names the old report; exit 1 is a carried conflict left in the new worktree for the builder (the line names it). Without `--carry` it starts clean, the old branch kept as `agentry/<id>.<n>`.
3g. Work built outside exec (an agent's worktree a drift row names, a hand branch) that should go on in this lane: `agentry lane exec adopt '<id>' --branch <b>` instead of `start`. It cuts the lane from main with `<b>`'s own commits picked (merges left out and named) and its worktree's uncommitted diff applied, leaves `<b>` and its worktree as they are (`cleanup:` says how to remove them after the land), and the first brief lists the adopted commits; `!` lines name adopted commits outside `owns`, with the `owns --add` line. Exit 2 refuses with nothing written (`nothing to adopt: use exec start`, a branch a ledger tracks or already adopted, a worktree mid-rebase or mid-merge); exit 1 is a carried conflict left in the new worktree, as for `restart --carry`.
4. `close` also works on a merged or stopped lane (to clear a pending episode). After `close`: call `episode_write` with `episode`, then run `afterwards` with the id it returns. Hand off: worktree, branch, verdicts, the gate record, and what's left (`/agentry:merge <id>`).

Show `guards` and `nested` whenever they are not empty. Lost track: `agentry lane exec show <id>`. Not in this lane: right-sizing, spec, plan or split; files under `.agentry/work/`; board edits by hand; merge and push.
